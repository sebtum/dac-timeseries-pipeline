## Findings — none contradict an ADR; all are additive

1. **The HTTP API is not CLI-only for database creation with retention** (resolves
   `docs/plans/M1.md`'s standing assumption 2's contingency in the other direction).
   `POST /api/v3/configure/database` with `{"db": ..., "retention_period": "365d"}`
   works and the retention is actually applied — confirmed via container logs
   (`CreateDatabaseOptions { retention_period: Some(31536000s) }`). Unlike
   `create token --admin`, a duplicate create returns a plain HTTP 409 with no
   exit-code-0 quirk, so idempotency detection is a status-code check, not text
   sniffing. `init_influx.py` never shells out.
2. **Core hard-caps at 5 non-internal databases** (confirmed empirically: a 6th create
   attempt returned HTTP 422 "Adding a new database would exceed limit of 5 databases";
   matches InfluxData's published Core-vs-Enterprise limits). Not in any ADR. Three
   databases is nowhere near it, but a future 4th distinct-retention tier would need
   Enterprise or reclaiming a slot — worth an `ASSUMPTIONS.md` note.
3. **A deleted database's slot is reclaimed on this build** (an older reported upstream
   bug where deleted databases kept counting toward the limit, influxdata/influxdb#25701,
   does not reproduce on 3.11.2 — verified directly: delete, then immediately create a
   new database, succeeds). Relevant to T5: its throwaway 1-hour-retention database can
   safely be created and dropped once per test/CI run indefinitely.
4. **The plant-policy shorthand `9mo` is not a literal the server accepts** — `POST
   .../database` with `retention_period: "9mo"` returns HTTP 400 ("expected a
   duration"). `.env.example`'s `9mo` is documentation of the plant policy only, never
   an actual config value; `parse_duration` in `init_influx.py` also rejects it
   (tested), so there's no path where someone copies that number in literally and gets
   a silently-wrong result — they'd get an immediate error instead.
5. **Resolved fork, confirmed by Sebastian**: an empty `INFLUX_PINNED_RETENTION` causes
   `create_database` to omit the `retention_period` key entirely (not send an empty
   string) — verified this produces `retention_period: None` server-side, the server's
   own native "no expiry" representation, rather than depending on undocumented
   empty-string handling.
