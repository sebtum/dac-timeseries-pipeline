## What was built

- `pipeline/rollup_run.py` — `run_rollup(raw_client, rollup_client, start, end,
  include, policy_version)`: queries `readings_numeric` in `dac_raw` via Flight SQL
  (`mode="reader"`, bound `$start`/`$end` parameters), floors each row to its 1-minute
  bucket, calls `pipeline.rollup.compute_rollup` per `(experiment_id, source, signal,
  bucket_start)` group, writes each result to `dac_rollup` as one point on a new
  `readings_rollup` measurement.
- `tests/integration/test_rollup_run.py` — 5 tests, `influx`-marked, two throwaway
  databases per test (raw + rollup), teardown in the fixture (T5's pattern).

## Memory shape — checked directly, not assumed (E-03, MISTAKES.md)

Every stage was checked separately rather than trusting the overall shape looked
streaming:
- Raw fetch uses `mode="reader"` (a genuine Arrow `RecordBatchReader`), not
  `mode="all"`, which materializes the whole result before returning — verified by
  reading the client's `_translate_stream_reader` source directly.
- Because the query is `ORDER BY time` and a 1-minute floor is a non-decreasing step
  function of time, at most **one bucket-minute is ever open at once** across every
  series combined — bounded by the measured 150-series cardinality (ADR-0006), not by
  row count in `[start, end)`.
- Buckets are flushed (aggregated + written) the moment the bucket boundary advances,
  not accumulated for the whole range. A range spanning months never holds more than
  one minute's samples or the whole range's output points at once.

This came from a direct correction mid-session: the first draft called
`.to_pylist()` on the whole query result and built one `dict` of every bucket in the
range before writing anything — the exact E-03 shape (streams in one stage, batches
in another). Caught before any file was written to disk.

## Findings

1. **`query_parameters` values must be JSON-serialisable.** Passing a `datetime`
   object directly raises `TypeError: Object of type datetime is not JSON
   serializable` inside the client — it JSON-encodes the parameter dict before
   Flight SQL ever sees it. Fixed by passing `start.isoformat()` / `end.isoformat()`.
   Confirmed the server compares these correctly against the `time` column.
2. **A column nothing has ever written to does not exist in the table's schema at
   all — it is absent, not nullable-and-null.** `SELECT mean FROM readings_rollup`
   raised `Schema error: No field named mean` against a fresh throwaway table where
   every written row happened to have `count_included = 0` (mean/std/median always
   omitted). Only bites if the *entire* table's history never once wrote the field;
   a real `dac_rollup` with any included sample anywhere is unaffected, but it means
   a downstream consumer selecting `mean` explicitly should not assume the column is
   always present on a freshly-created database. `Point.field(name, None)` itself
   silently drops the field (verified directly: `p.field("y", None)` produces no
   `y=...` in line protocol) — this isn't a bug in the omission, it's a property of
   how Core evolves table schema.
3. **`SHOW DATABASES` is not a supported SQL statement over Flight SQL** — errors
   `This feature is not implemented`. Listing databases (used here only to confirm no
   throwaway test database leaked) requires the `influxdb3` CLI (`show databases`)
   or the HTTP configure API with the right query shape, not a SQL query through the
   Python client. Not a T9 blocker, just a gap from what T1's spike covered.
4. **U-05 (Core's ~72h single-query span limit) was not exercised.** The test
   fixture spans minutes, nowhere near the limit. Per the plan, this is stated
   rather than worked around: `run_rollup` does not pre-check span width, and if a
   caller passes a too-wide range the query raises during iteration and that error
   propagates unchanged. Not verified against an actual over-limit query this
   session — a real 6-experiment, 2-hour-each rollup call would call `run_rollup`
   once per experiment (well under 72h each), so it isn't expected to bite at M1
   scale, but the failure mode itself remains unobserved.

## Design choices made without a governing ADR (trivia, redirectable)

- Rollup measurement name: `readings_rollup`. Nothing in ADR-0011/ADR-0006 names it;
  picked to read naturally alongside `readings_numeric`/`readings_state`.
- Query style: Flight SQL bound parameters (`query_parameters={...}`) over string
  formatting, for the same reason it would matter if the input were ever untrusted.
