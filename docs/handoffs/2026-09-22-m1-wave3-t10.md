## What was built

- `.github/workflows/ci.yml` — added an `integration` job alongside the untouched `lint`
  job.
  - **Postgres**: a native Actions `services:` container (`postgres:16.6`), credentials
    matching `.env.example`'s defaults (`dac`/`dac`/`changeme_local_only`) so
    `bootstrap_influx_token.py`'s auto-seed-from-`.env.example` needs no CI-specific
    override. Actions blocks the job's steps until the service's own healthcheck
    (`pg_isready`) passes, and fails the job if it never does — this is the mechanism, not
    a step I wrote.
  - **InfluxDB 3 Core**: *not* a `services:` container — Actions service containers can't
    override an image's command past its entrypoint, and Core's entrypoint
    (`influxdb3 serve`) requires `--node-id`/`--object-store`/`--data-dir` with no defaults
    (`docs/spikes/U-13-core-token-bootstrap.md`). Brought up instead with a plain
    `docker run` using exactly the flags the spike verified, including
    `--disable-authz health` so the readiness wait needs no token yet.
  - Readiness wait is a `curl`-in-a-loop against the published port from the runner host
    (`timeout 60 bash -c 'until curl -sf .../health; do sleep 2; done'`), not
    `docker inspect`'s health status — simpler, and equivalent to what
    `bootstrap_influx_token.py` already does internally for the same endpoint.
  - Sequence after both services answer: `bootstrap_influx_token.py`,
    `python -m scripts.migrate`, `python scripts/init_influx.py`, then `pytest -v` — the
    order `docs/plans/M1.md`'s T10 section specifies. `scripts/init_influx.py` is invoked
    bare (it imports nothing from `pipeline/`); `scripts.migrate` is invoked as `-m` per
    T6's finding.
  - **Skip-as-failure guard**: pytest's exit code doesn't reflect skipped tests, so the
    acceptance criterion "a skip in CI is a failure in CI" is enforced explicitly —
    `pytest -v` output is piped to a log (`set -o pipefail` so a real test failure still
    fails the step) and grepped for `N skipped`; a match raises `::error::` and exits 1.
  - `docker logs dac-influxdb` on failure, `docker rm -f dac-influxdb` always — Postgres
    teardown is automatic (Actions owns the service container's lifecycle).

## Verification performed

- **YAML parses** (`python -c "import yaml; yaml.safe_load(...)"`) — syntax only.
- **Not run locally end-to-end.** The repo's real dev stack (`dac-influxdb`,
  `dac-postgres`) was already up and healthy on this machine, holding the actual project
  databases/schema built across T4–T9 — reusing those container names or the repo's real
  `.env` for a throwaway CI-style dry run risked clobbering live state
  (`bootstrap_influx_token.py` writes into the same `.env` unconditionally). Ran a
  container inventory (`docker ps -a`) to confirm the collision before deciding not to,
  rather than assuming. A true dry run would need distinct container names/ports and a
  scratch `.env`, which is more machinery than the actual target (GitHub Actions, a clean
  environment every run) needs built for it.
- Every command in the new job (the `docker run` flags, the token bootstrap, `-m
  scripts.migrate`, `python scripts/init_influx.py`) is otherwise identical to command
  sequences already exercised live in T1/T4/T5/T6/T7/T9's sessions against this same image
  pin and script set — not re-verified here, cited from those handoffs.
- **Not yet run in GitHub Actions.** T10's own acceptance criterion ("workflow is green on
  the branch, with the run URL recorded") is only checkable once this is pushed — that's a
  shared/visible action, held for Sebastian's go-ahead rather than done unilaterally.

## Findings

1. **Actions service containers cannot run InfluxDB 3 Core directly** — confirmed by
   design, not by trying and failing: the `services:` block only exposes `image`, `env`,
   `ports`, `volumes`, and `options` (docker *create*-time flags); there is no field for a
   command/entrypoint override, and Core's entrypoint has no usable defaults. This is why
   Postgres and InfluxDB are brought up two different ways in the same job. Not a
   contradiction of anything — `docs/plans/M1.md`'s own T10 wording already distinguishes
   "Postgres as a service container" from "InfluxDB brought up with T1's verified flags",
   which reads as already anticipating this.
