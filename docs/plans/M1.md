# M1 Plan — task breakdown and acceptance criteria

Date: 2026-08-31   Milestone: M1   Deliverable: A

The fourth Plan-phase output required by [`../ROADMAP.md`](../ROADMAP.md) § *The four-phase
protocol*: the milestone broken into tangible tasks, each executable by an agent that has not seen
the conversation, with acceptance criteria that are checkable statements tracing back to the M1
verify criteria rather than inventing a second standard.

The other three outputs already exist: the Discuss record ([`../discuss/M1.md`](../discuss/M1.md)),
the ADRs ([0011](../decisions/ADR-0011-retention-tiering-rollup.md),
[0012](../decisions/ADR-0012-postgres-migrations-metadata-loader.md)), and the verify criteria in
`../ROADMAP.md` § M1.

## Three calls made in this phase

Recorded here rather than in an ADR: none of them changes an architecture decision, and two of
them are about *how the work is sequenced*, which is not ADR material.

**U-04 is neutralised, not resolved.** The rollup splits into a pure aggregation function
(T8 — locus-independent, unit-testable) and a thin driver (T9 — queries `dac_raw`, writes
`dac_rollup`). Whether a Processing Engine plugin or an external scheduled job *calls* the driver
is a wrapper question, and it is deferred to M3 where M3's verdict actually exists. This is the
same seam ADR-0011 already argues along: the rollup is a cache, and what recomputes it is
separable from what it computes. U-04 stays open; no M1 task is blocked by it.

**The M1 CI increment runs both services in GitHub Actions.** Postgres as a service container,
InfluxDB 3 Core brought up in the workflow. ADR-0009 claims the stack comes up from a clean
checkout; running it only locally would leave that claim exactly as untested as the configuration
ADR-0008 refused to stub. U-02 is untouched — nothing in the job reads the dataset.

**Local raw retention is 1 year, against the 9-month plant policy.** ADR-0011 already requires
retention to be a *parameter* of the init script rather than a constant, with the local value
committed alongside its reason; this supplies the local value. All six experiments (2026-03-02 …
2026-06-15) clear a 1-year window with margin — the earliest, `EXP_004`, would not reach the
boundary until 2027-03-02, where 9 months locally would expire it around 2026-12-02 and do so
silently (C-06). The plant policy is unchanged and stays documented as the default.

## Standing assumptions

Implementation consequences, not new design calls. Any one of them turning out wrong bounces back
to Discuss per the protocol rather than being decided inside an implementation.

1. **The M1 proofs run against a small synthetic fixture written directly into Influx, not the raw
   CSV.** Ingestion is M2. Verify criteria V2 ("raw preserved unchanged, by query") and V3
   ("downsampling matches a hand-computed aggregate") are not satisfiable at M1 any other way, and
   a fixture keeps them honest — the expected aggregate is computed by hand from values chosen for
   the test, never read back from the thing under test.
2. **Scripts are Python against the HTTP API / `influxdb3-python`, not shell wrapping the CLI**
   (ADR-0003), because the same code then runs from a test. If T1 finds that creating a database
   with a retention period is CLI-only on the pinned build, that is a finding to record and the
   script shells out to `influxdb3` inside the container.
3. **Retention values are read from the environment**, never literals in source. `.env.example`
   carries the local value and the plant-policy value side by side, each with its reason.

## Execution model

Five roles, four waves, one hard rule: **no two tasks running in the same wave write the same
file.** Every task names the files it owns.

| Role | Owns | Tasks |
|---|---|---|
| Spike | `docs/spikes/` | T1 |
| Runtime | compose, env, deps, test harness | T2 |
| Influx | init script, behavioural proofs | T4, T5 |
| Postgres | migrations, runner, loader | T6, T7 |
| Rollup | aggregation, driver | T8, T9 |
| Docs/CI | schema reference, workflow, tracking files | T3, T10, T11 |

```
Wave 0   T1 spike (blocking — nothing else starts)
           |
Wave 1   T2 runtime  ||  T3 schema doc  ||  T8 rollup aggregator (pure)
           |                                      |
Wave 2   T4 → T5 influx  ||  T6 → T7 postgres      |
           |                       |               |
Wave 3   T9 rollup driver  ||  T10 CI  ||  T11 tracking files
           |
Wave 4   T12 verify pass
```

**Tracking-file rule.** `ROADMAP.md`, `ASSUMPTIONS.md`, `MISTAKES.md` and `decisions/README.md`
are written **only** by T11. Every other task ends with a handoff note stating what it built, what
it found that contradicts an ADR, and anything worth a `MISTAKES.md` entry; T11 transcribes. This
exists to stop parallel agents racing on one file — it does not relax `CLAUDE.md`'s rule that
mistakes are logged the moment they surface.

**Commit checkpoints:** after each wave, then `M1: time-series data model` after Wave 4.

## Wave 0

### T1 — Verify U-13: InfluxDB 3 Core first-boot token behaviour

`ROADMAP.md` § M1 Execute makes this the first step, explicitly *before* the compose file.
ADR-0008 and ADR-0009 both assert Core mints an admin token on first boot; the claim has never
been tested in this repo, and it shapes the compose file, the `.env` bootstrap and the CI workflow.

**Reads:** ADR-0008, ADR-0009 (exception 1), `ASSUMPTIONS.md` U-13.
**Owns:** `docs/spikes/U-13-core-token-bootstrap.md` (new directory).

Start the image by hand (`docker run`, not compose) and answer, with pasted command output:

- Which exact tag is the Core 3.x line, and is it a stable pin (not `latest`)?
- What does the container require at startup — `--object-store`, `--node-id`, `--data-dir`?
- Does it mint an admin token on first boot, and can that token be captured **non-interactively**?
- Does `create database --retention-period` exist on this build, and what value syntax does it
  accept (`9mo`, `365d`, `1h`)?
- Does `influxdb3 show databases` / `GET /api/v3/configure/database` report the retention period
  back, or is [influxdb#27082](https://github.com/influxdata/influxdb/issues/27082) still
  reproducible here?
- Minimum flags to bring the same container up in a GitHub Actions runner.

**Acceptance criteria**
- [ ] The spike note exists and answers all six questions with pasted command output, not prose
      recollection.
- [ ] It states an exact image tag to pin, and that tag resolves (`docker pull` succeeds).
- [ ] The token answer is either *works non-interactively*, with the exact command, or *does not*,
      with what failed. If it does not, the note says so plainly and flags that ADR-0008/0009's
      assertion needs correcting — it does not invent a workaround.
- [ ] The retention-flag answer includes one worked example that actually created a database.
- [ ] Every container and volume the spike created is removed afterwards.

**Bounce condition:** if Core cannot bootstrap a token non-interactively, U-13's *policy* (auth on
locally) is contradicted by its *mechanism*. Stop and return to Discuss rather than quietly
deciding auth-off inside an implementation.

- `.env.example` — `INFLUX_RAW_RETENTION=365d`, `INFLUX_ROLLUP_RETENTION=365d`,

- [ ] `docker compose down -v`, then up and bootstrap again, works — run deliberately once

- [ ] `git status` shows no `.env` after the bootstrap runs.
- [ ] `.env.example` carries both the local and the plant-policy value for every retention
      parameter, each with its reason.
- [ ] No Grafana service exists in the file, commented or otherwise.
- [ ] `pip install -r requirements.txt` succeeds from clean; `ruff check .` and

- [ ] `pytest` with no containers running reports skips, not errors.

### T3 — `docs/schema.md`: the compact schema reference

The hand-to-someone artifact for deliverable A. Pure documentation derived from settled ADRs — no
new decisions, no invented numbers.

**Reads:** ADR-0005, ADR-0006, ADR-0011, ADR-0012, `reports/pre_ingest_census.md`,
`task/DATA_DICTIONARY.md`.
**Owns:** `docs/schema.md`.

One skimmable page covering: the two tables with their tag set and field types and why the split
exists; the 150-series cardinality with its source; ADR-0011's four-tier table with both the
plant-policy and local retention values; the rollup column set with the verdict-independent /
verdict-dependent split visible in the layout and the population-std convention stated; the volume
arithmetic (1,059,840 points/day ≈ 387 M points/plant-year, 60:1 at one minute); the rollup-lag
invariant; and why `readings_state` is never rolled up.

**Acceptance criteria**
- [ ] `docs/schema.md` exists and covers all seven items above.
- [ ] Every number traces to a cited source — an ADR, the census report, or the data dictionary.
      No number appears without one.
- [ ] Cardinality is stated as **measured**, with the measurement named (V1).
- [ ] The volume arithmetic is reproducible from the stated per-rate signal counts (V6).
- [ ] The rollup-lag invariant is stated with its consequence — buckets freeze carrying a stale or
      missing aggregate, with no recovery (V7).
- [ ] No design decision appears here that is not already in an ADR.

### T8 — Rollup: the pure aggregation function

The half of the rollup U-04 does not touch. A pure function is a unit test, which is the entire
point of splitting it out.

**Reads:** ADR-0011 (rollup schema, quality policy, the sufficient-statistics argument).
**Owns:** `pipeline/rollup.py`, `tests/unit/test_rollup.py`.

A function over the samples of one `(experiment_id, source, signal, bucket_start)` plus an
**injected inclusion predicate**, returning ADR-0011's column set:

```
count_all, min_all, max_all, sum_all, sumsq_all      verdict-independent
count_included, mean, std, median                    verdict-dependent
count_good, count_uncertain, count_bad               composition
policy_version                                       provenance
```

The predicate is a parameter, not a constant — at M1 the stated placeholder is
`quality == 'GOOD'`, and M3 replaces it. `UNCERTAIN` is excluded. Std is **population**
(denominator n). Buckets are 1 minute, floor-aligned.

**Acceptance criteria**
- [ ] Against a hand-built bucket whose aggregates were computed by hand rather than by the
      function, every returned column matches (V3, unit half).
- [ ] The verdict-independent columns are identical under two different predicates over the same
      samples; the verdict-dependent columns differ.
- [ ] `count_good + count_uncertain + count_bad == count_all` for every test bucket.
- [ ] An n=1 bucket returns `std = 0.0` — not an error, not null. The population convention is what
      makes it defined, and all four ambient signals hit n=1 at 1-minute buckets.
- [ ] A bucket with every sample excluded returns `count_included = 0`, verdict-dependent columns
      null, and `min_all` / `max_all` still populated.
- [ ] Pooling two adjacent buckets' `(count_all, sum_all, sumsq_all)` reproduces the aggregate over
      their union — the claim ADR-0011 rests permanence on, asserted rather than assumed.
- [ ] `policy_version` is a parameter, and no test passes with it silently defaulted.
- [ ] `pipeline/rollup.py` imports nothing from InfluxDB.

## Wave 2

### T4 — Influx init: three databases, parameterised retention

Core has no declarative configuration (ADR-0009), so "as code" here means an idempotent script.

**Reads:** ADR-0009, ADR-0011, T1's spike note, `.env.example`.
**Owns:** `scripts/init_influx.py`, `tests/integration/test_influx_init.py`.

Create `dac_raw`, `dac_rollup`, `dac_pinned` with retention from the environment; re-running is a
no-op. **Before creating `dac_raw` the script asserts the configured retention covers
`min(start_time)` from `data/raw/experiments.json`, and refuses otherwise** — C-06 turned into
code. A retention period is a claim about age relative to *now* and the failure mode is silent, so
the guard belongs at creation time.

**Acceptance criteria**
- [ ] Against a clean stack, one run creates exactly three databases; a second run creates nothing,
      changes nothing, exits 0.
- [ ] With `INFLUX_RAW_RETENTION=90d` the script **refuses** to create `dac_raw` and names the
      experiments that would be excluded (V4) — asserted by a test, with `EXP_004` named first.
- [ ] With the local `365d`, all six experiment windows clear the guard and creation proceeds.
- [ ] `dac_pinned` is created with no retention period at all, not with a very large one.
- [ ] No retention literal appears in the source; every value is read from the environment.

### T5 — Behavioural proofs against a live Core

Two verify criteria that can only be settled by observing the server. `influxdb3 show databases`
reported no retention period on Core 3.7.0 (influxdb#27082), so asserting on configuration could
silently assert nothing.

**Reads:** ADR-0006, ADR-0011 (consequences), `ROADMAP.md` § M1 Verify.
**Owns:** `tests/integration/test_retention.py`, `tests/integration/test_raw_preservation.py`.

- *Retention (V5)* — create a throwaway database with a **1-hour** retention period, write one
  point at `now − 2h` and one at `now − 5m`, query both back, assert the first is absent and the
  second present, drop the database.
- *Raw preservation (V2)* — write a synthetic fixture covering both tables (a high-precision float,
  a negative value, and both categorical signals as literal strings), read it back, assert
  byte-for-byte identity with what was written. ADR-0006's "demonstrable by query, not asserted",
  exercised before ingest exists.

**Acceptance criteria**
- [ ] The retention test passes, and its throwaway database is dropped **even when the test fails**
      — teardown in a fixture, not at the end of the test body.
- [ ] It asserts on query results, never on `show databases` output or the configure API.
- [ ] `readings_state` round-trips `STEADY_STATE` / `OPEN` as strings — a test that would fail if
      anything encoded them as integers (ADR-0006's rejected Option 1).
- [ ] A float round-trips identically at full precision.
- [ ] Both tests are marked `influx` and skip cleanly with no server running.

### T6 — Postgres: migration runner and versioned schema

ADR-0012 Option 3. The runner is deliberately small, and ADR-0012 names three properties it must
have **or it is worse than a real tool**: deterministic ordering, an advisory lock, a checksum.

**Reads:** ADR-0012 in full (the SQL is in it), ADR-0005, ADR-0009 exception 3.
**Owns:** `migrations/*.sql`, `pipeline/pg_migrate.py`, `scripts/migrate.py`,
`tests/integration/test_migrations.py`.

- `0001` — the `experiment` table, with **nullable** `operator`, `sorbent_batch`, `notes` and the
  nominal parameters, so `EXP_003` / `EXP_005` / `EXP_006` survive the load as NULL.
- `0002` — the `field_source` enum, `experiment_field_source`, `is_manual()`,
  `record_experiment_provenance()` and the `experiment_provenance` trigger, transcribed from
  ADR-0012 rather than re-derived.

**Acceptance criteria**
- [ ] Against an empty database, `python scripts/migrate.py` applies every migration and exits 0
      (V10).
- [ ] A second run applies nothing and exits 0 (V10, no-op half).
- [ ] Ordering is deterministic and does **not** depend on filesystem order — asserted by a test,
      not by inspection.
- [ ] A migration file edited after being applied makes the next run **fail loudly**, naming the
      version; it does not silently skip.
- [ ] Two concurrent runners cannot double-apply — a test holds the advisory lock and asserts the
      second blocks or fails rather than proceeding.
- [ ] A deliberately failing migration leaves the schema **unchanged**: the transactional-DDL claim
      ADR-0012 rests the hand-rolled-runner defence on, tested rather than asserted.
- [ ] No `docker-entrypoint-initdb.d` directory is mounted anywhere (ADR-0009 exception 3).

### T7 — Postgres: the `experiments.json` loader with per-field provenance

ADR-0012 Option C. The load-bearing property is that **a re-run cannot revert a manual
correction** — the entire justification for ADR-0005 putting metadata in Postgres at all.

**Reads:** ADR-0012 (loader SQL and consequences), ADR-0005, `data/raw/experiments.json`.
**Owns:** `pipeline/metadata_loader.py`, `scripts/load_experiments.py`,
`tests/integration/test_metadata_loader.py`.

Idempotent upsert keyed on `experiment_id`, **no hard deletes**, `SET LOCAL app.actor = 'loader'`,
one `CASE WHEN is_manual(...)` per correctable column. `experiments.json` stays the immutable
source under `data/raw/`; Postgres is where corrections land.

**Acceptance criteria**
- [ ] After one run all six experiments are queryable with correct values (V8).
- [ ] `EXP_003.notes`, `EXP_005.sorbent_batch` and `EXP_006.operator` are **NULL** — not `''`, not
      a default (V8).
- [ ] **Null case (V9):** set `EXP_005.sorbent_batch` manually, re-run, the manual value survives —
      the case a plain upsert loses.
- [ ] **Wrong-non-null case (V9):** set `EXP_001.operator` to something different from the JSON,
      re-run, the manual value survives — the case `COALESCE` would *not* have caught, and the
      reason Option C beat Option B.
- [ ] Provenance records `manual_override` for a manually changed field and `loader` for a
      loader-written one.
- [ ] A change made with `app.actor` **unset** is recorded as `manual_override` — the fail-safe
      default, tested.
- [ ] The documented escape hatch works: deleting the `experiment_field_source` row hands the field
      back to the loader and the next run updates it.
- [ ] **The trigger's column array matches the table's correctable columns** — a test that fails if
      someone adds a column and forgets the trigger. ADR-0012 names this coupling as the price of a
      static list and says it should be covered by a test.
- [ ] A row removed from a copy of `experiments.json` is **not** deleted from the database.

## Wave 3

### T9 — Rollup driver: `dac_raw` → `dac_rollup`

The thin half. It queries, calls T8's function, and writes. Everything interesting lives in T8;
everything U-04-shaped lives outside this file.

**Reads:** ADR-0004 (Core, SQL, U-05), ADR-0011, T8's module.
**Owns:** `pipeline/rollup_run.py`, `tests/integration/test_rollup_run.py`.

Takes a time range, a predicate and a `policy_version`; queries `dac_raw`, aggregates into 1-minute
buckets via `pipeline.rollup`, writes to `dac_rollup`. Numeric signals only. Re-running over the
same range overwrites rather than duplicates — the rollup is a cache, not a record. **Nothing in
this file schedules itself**; a docstring records that *who calls it* is U-04, open until M3.

**Acceptance criteria**
- [ ] Against a synthetic fixture in `dac_raw` with known values, the resulting `dac_rollup` rows
      match a hand-computed aggregate under the stated placeholder predicate `quality = 'GOOD'`
      (V3, end-to-end half).
- [ ] The placeholder is **stated in the output** — `policy_version` on every written row
      identifies it — so nobody later reads the M1 rollup as M3's verdict.
- [ ] Re-running over the same range leaves the same row count, not double.
- [ ] No `readings_state` data reaches `dac_rollup`.
- [ ] A bucket spanning a gap produces a `count_all` reflecting actual samples, so a 3-sample
      minute and a 60-sample minute stay distinguishable.
- [ ] The module contains no scheduling, no trigger registration, no cron wiring.
- [ ] If Core's query-span limit (U-05) is hit, the failure is explicit and recorded in the handoff
      note — not worked around silently.

## Known risks

- **T1 is a genuine spike and can invalidate what follows.** If Core will not bootstrap a token
  non-interactively, or `--retention-period` is absent on the pinned build, Wave 1 does not start —
  it returns to Discuss. That is why T1 blocks everything.
- **Core in GitHub Actions is unproven.** Postgres as an Actions service is routine; Core is not,
  and it needs object-store and node-id flags. T1 answers this. If it cannot be made to come up,
  T10 falls back to Postgres-in-CI with the Influx tests marked local — recorded as a stated
  limitation, not a silent scope cut.
- **U-05 can surface early.** T9 queries a range; if the fixture spans more than Core's ~72h
  single-query limit it bites here rather than at M2.5. Keep the fixture small enough that it does
  not — and if it does, that is a finding, not a workaround.
- **What M1 verifies about the rollup is machinery, not policy.** `quality = 'GOOD'` is a
  placeholder and `UNCERTAIN` is excluded. M3 supplies the real predicate and the rollup is
  rebuilt. If that split is not visible in `docs/schema.md` and in `policy_version`, someone later
  reads the M1 rollup as an answer.
