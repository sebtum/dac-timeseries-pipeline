# M1 Discuss — time-series data model: retention, tiering, and the metadata path

Date: 2026-08-30 → 2026-08-31   Milestone: M1   Deliverable: A (with F touched via ADR-0005)

The Discuss-phase record for M1: what was put on the table, what was decided, what was corrected,
and what was still open when the phase closed. Decisions themselves live in `../decisions/`; this
document is the reasoning trail that produced them, kept because the *route* to a decision is what
gets attacked in review, and it is not recoverable from the ADR alone.

### Facts supplied, with their sources

**Volume.** 520,005 rows / 31,877,732 bytes of CSV = 61.3 bytes/row as text; six experiments × 2 h.
By nominal rate: 9 signals at ~1 Hz, 4 at ~0.5 Hz, 6 at ~0.2 Hz, 4 at ~1/60 Hz, 2 event-based.
Extrapolated to one plant logging continuously: **1,059,840 points/day ≈ 387 M points/plant-year**,
of which the 1 Hz group is 73%. Rollup ratios are fixed arithmetic — 60:1 at one minute, 300:1 at
five. Parquet bytes-per-point was deliberately *not* estimated; it is an M2.5 measurement.

**Constraints, verified against documentation rather than asserted from memory:**

- A retention period in InfluxDB 3 Core is set at `create database` and **cannot be changed
  afterwards**; it is **per-database, not per-table**.
- Core enforces retention **at query time** — expired points are filtered from results while still
  in storage, deleted asynchronously. The failure mode is therefore *silent*.
- Core ships the Processing Engine with `every:`/`cron:` scheduled triggers; a scheduled plugin can
  query history and write to another database.
- **No tier of InfluxDB has per-range retention exemption.** Enterprise adds *updatable* database
  retention and *table-level* retention; it has no "pin this window" feature.
- InfluxDB 3 stores Parquet in an object store (`--object-store` = file / s3 / google / azure).
- `influxdb3 show databases` and `GET /api/v3/configure/database` reported **no retention period**
  on Core 3.7.0 ([influxdb#27082](https://github.com/influxdata/influxdb/issues/27082), fixed in
  #27107) — which is why the M1 retention check is behavioural, not configurational.

## How the decisions moved

Four round-trips. The corrections are the useful part.

### Round 1 — the first retention proposal

**Proposed:** 90 days raw, 1 year at 1-minute resolution, min/max/avg/std/median, cold storage at
"maybe a big cloud provider", and pinned high-resolution intervals via "a feature to pin them".

Two things were genuinely strong and stayed: framing retention as a **stakeholder decision not yet
had** (the electrochemical lab manager) with a stated default rather than an invented number; and
reaching for **min/max** rather than mean alone, which is what stops a rollup erasing the voltage
transient deliverable J asks you to walk through.

Corrected:

- **[C-06](../MISTAKES.md) — 90 days deletes five of six experiments.** The experiments run
  2026-03-02 … 2026-06-15 against an August wall clock; 90 days back is 2026-06-01, so only
  `EXP_005` survives. Worse, it fails silently: the write succeeds and the data is merely
  invisible, which would have made M2's "row counts reconcile CSV → Influx" criterion pass when
  counting writes and fail when querying back — pointing the debugging at the wrong component.
  *Principle:* a retention period is a claim about age relative to *now*, so it must be checked
  against the timestamp span of the data that will be written under it. Backfill and retention are
  natural enemies.
- **[C-07](../MISTAKES.md) — the pin feature does not exist.** Retention in Core is per-database,
  uniform and immutable; there is no per-range hold. Pinning is build-work, and once it is
  build-work the hidden design problem surfaces: **pinning is retroactive**, so the raw retention
  window doubles as a deadline for someone to notice.

Also flagged as gaps: `count` missing from the rollup (without it a 60-sample minute and a
3-sample minute are indistinguishable and every downstream mean is mis-weighted); `UNCERTAIN` had
no rule; the raw-preservation guarantee from ADR-0006 was unaddressed under retention; and the
rollup design was implicitly numeric-only, saying nothing about `readings_state`.

One further note on the 1-minute interval: the number is right but the stated reason — LCM of the
sample periods — is not the criterion. The floor is the **slowest polled rate** (60 s ambient), so
every signal gets a non-empty bucket. They coincide here; they would not if ambient were 90 s.

### Round 2 — revision, and a correction in the other direction

**Proposed:** 9 months raw; a separate unlimited-retention database for intervals of interest;
`count` added; `UNCERTAIN` treated as `BAD`; the rollup keyed on M3's pipeline verdict; pinning
triggered by `valve_state` / `process_state` changes with post-shutdown data discardable; auth
enabled locally with the token bootstrap verified rather than assumed; versioned SQL migrations
with a small Python runner and per-field provenance in the loader; Processing Engine plugin
preferred for the rollup.

9 months checks out against the data — all six experiments fall inside it.

The unlimited-retention database is the correct workaround, and it makes the pin mechanism
concrete: **a pin is a copy of a time range into a tier that never expires**, not an exemption.

**[C-08](../MISTAKES.md)** — the claim that Enterprise allows pinning relocated the C-07 error
rather than fixing it. Enterprise adds updatable and table-level retention, not per-range
exemption. Secondary point: describing a correct design as a budget workaround concedes ground
that does not need conceding.

**[E-04](../MISTAKES.md) — my error, corrected by Sebastian.** I had argued that `avg`/`std`/
`median` per bucket were insufficient because std cannot be re-aggregated. Wrong: with `count` and
`mean` retained, `Σx = n·m` and `Σx² = n·(s² + m²)`, so pooling is exact and `(count, mean, std)`
carries the same information as `(count, sum, sumsq)`. The pushback was correct. Sum and sumsq are
still stored, but for two much narrower reasons: *sample* std leaves an n=1 bucket unrecoverable —
which happens for all four ambient signals at 1-minute buckets — and pooling raw sums is
associative addition with no n-vs-n−1 convention to get wrong. Median remains genuinely
non-mergeable.

Further challenges raised in this round: the state-change pinning trigger gates an irreversible
action on two signals that have not been profiled (C-02's principle — validate the gate before
trusting the gating); "discard after shutdown" was ambiguous between deletion and downsampling, and
deletion would break `E = ∫P dt`; and a plain upsert in the metadata loader would write the file's
null straight over a Postgres-side correction, silently undoing the exact capability ADR-0005 was
written to provide.

### Round 3 — push-back accepted, and a sharpening from the other side

Sebastian pushed back that the corrections were drifting toward unlimited retention, "amazing but
not practical". Accepted, and it was the right call: the December expiry is not an architecture
flaw, it is two purposes colliding on one number. **Retention became a parameter of the init
script rather than a constant in it** — 9 months as plant policy, a different value for the local
demo, committed with its reason. The residual risk (unexercised config is untested config) is
handled by a throwaway 1-hour-retention database in the verify criteria rather than by softening
the policy.

**The sharpening that changed the design came from Sebastian:** the verdict does not evolve
per bucket — what matters is the verdict in force *at the moment retention expires*. That is
correct and it simplifies things. Inside the raw window a bucket's rollup is provisional and
disposable; it becomes permanent only when raw drops out from under it. Two consequences follow:

- `policy_version` is still required, but for a better reason — across the table, buckets crossed
  the expiry line under different policy generations, and that mixture is permanent and accumulates
  at the trailing edge.
- **Rollup lag must stay strictly below the raw retention period**, or buckets freeze carrying a
  stale or missing aggregate with no recovery. That is deliverable H's named failure mode — every
  point still looks individually fine while the pipeline has stopped moving data — arrived at from
  this design rather than recited.

And the framing worth keeping: raw retention is not "how far back can we look", it is **"how far
back can we still change our mind"**.

### Round 4 — the remaining ambiguities

- **Is the data experiment-only, or does the rig run 24/7?** For this dataset, settled: every row
  carries an `experiment_id` and all six runs are 7200 s with explicit start/end. For the
  architecture, deliberately not assumed — deliverable H frames the CSV as a historian export and
  historians are continuous. So **pins are keyed by time range, never by experiment identity**, and
  `experiments.json` is one *producer* of pinned ranges rather than the definition of one.
  Registered as U-17, neutralised rather than blocking.
- **Detecting unlabeled events** — scoped across phases, none of it blocking M1. M2.5 *measures*
  (ADR-0010 already scopes run-lengths and consecutive-difference distributions; an unlabeled
  transition is a large consecutive difference, and the continuous-signal-vs-event-stream
  disagreement count is added there). M3+ *decides the rule*, because a threshold is remediation
  and fitting one inside the profiling milestone is the C-02 failure. M1 needs neither: the pin
  mechanism takes a range and copies it.
- **Post-shutdown data** — configurable retention window, not deletion. Anchored on the
  experiment's `end_time` from metadata, which cannot go missing, rather than on the `SHUTDOWN`
  event.
- **`readings_state`** — keep every event, longest tier, no rollup, no metrics. ~73 rows across all
  six experiments. The reason is semantic rather than size-based: written on change, so an empty
  bucket means *no change*, not *no data* (C-01), and aggregating them repeats the failure ADR-0006
  rejected integer encoding to avoid. The near-event retention window must be **symmetric** —
  interpreting a LOAD_CHANGE needs the pre-transition baseline as much as the response.

## What was settled

**Retention and tiering** ([ADR-0011](../decisions/ADR-0011-retention-tiering-rollup.md)) — three
databases, forced by Core's per-database immutable retention, plus a cold Parquet tier:

| Tier | Database | Retention |
|---|---|---|
| Raw | `dac_raw` | 9 months (plant policy; parameterised) |
| Rollup | `dac_rollup` | 1 year, 1-minute buckets, numeric only |
| Intervals of interest | `dac_pinned` | none |
| Cold | object storage | lifecycle policy, read by DuckDB/Athena/Spark |

Rollup columns split by verdict dependence — `count_all, min_all, max_all, sum_all, sumsq_all`
(permanent ground truth) against `count_included, mean, std, median` (policy-bound), plus
`count_good / count_uncertain / count_bad` and `policy_version`. Population std (denominator n) is
the stated convention.

**Postgres path** ([ADR-0012](../decisions/ADR-0012-postgres-migrations-metadata-loader.md)) —
versioned SQL applied by a small Python runner (safe specifically because Postgres has
transactional DDL), with the replacement trigger for a real tool written into the ADR.
`experiments.json` is bootstrap data loaded by an idempotent upserting loader with **per-field
provenance recorded by trigger**, so a re-run cannot revert a manual correction. Chosen over the
`COALESCE` fix because that only protects against nulls, not against a wrong non-null value in the
file overwriting a correction.

**D6** — no metadata field is duplicated into InfluxDB tags, so ADR-0006's 150-series cardinality
is unchanged.

## Open on exit

- **U-04 — where the rollup executes.** The stated preference is a Processing Engine plugin, but
  the rollup was scoped to consume M3's Python pipeline verdict, and a plugin cannot read a verdict
  that never materialises into InfluxDB (U-09, open until M3). Second axis: a plugin's CI check is
  an integration test needing a running server with the engine enabled and a trigger installed,
  where an external job is a unit test — and U-02 bites harder on the former. Resolve by
  materialising the verdict into InfluxDB, or by running the rollup where the verdicts already are.
- **U-13 — mechanism unverified.** The policy is settled (auth on locally, scripted bootstrap,
  gitignored `.env`, no secrets manager). Whether Core mints its admin token on first boot the way
  ADR-0008 and ADR-0009 both assert has still not been tested in this repo. It is the first M1
  Execute step and must precede the compose file.
- **A-03** — the retention numbers are defaults standing in for a conversation with the process
  owners. The tier *shape* is unaffected by whatever they say.
