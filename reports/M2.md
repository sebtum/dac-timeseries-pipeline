## What I decided, and what I turned down

Each line is the plain decision; the reason and the rejected option are under Details.

1. **Trust each timestamp's own offset, store UTC, reject a timestamp with no offset.**
   Details: ambient writes a fixed `+02:00` and lines up with its experiment only when the offset
   is honoured. Rejected: assume UTC, which is a silent fix. ADR-0013 D1.
2. **Never write to a database that does not exist.**
   Details: observed on 3.11.2, a write to a missing database creates it with no retention and
   uses one of the five slots. Ingest lists databases first and exits 2. Rejected: let the write
   create it. ADR-0013 decision 1.
3. **Save the counts from the database, not from the writer.**
   Details: after writing, ingest asks InfluxDB how many points each series holds, one experiment
   and one day at a time, so the roughly 72-hour query limit never applies. A lost write, a
   retention window hiding points or a leftover point from an older file all show up as an
   unbalanced series and exit 4. Rejected: count on write.
4. **A refused line fails the whole batch, and only connection errors and server errors are
   retried.**
   Details: `accept_partial=False` on the v3 endpoint; 4 tries, waits of 1, 2 and 4 seconds.
   Rejected: retry everything (resending a refused line cannot help).
5. **When two readings claim one instant: better flag, then a present value, then the smaller
   number (alphabetical for text).** Both readings are kept in the conflicts table, one row per
   discarded reading.
   Details: content only, so file order cannot matter. All 10 real conflicts have equal flags, so
   the smaller-value rule decides all ten. M3 should mark those instants as suspect and not trust
   the winner. Rejected: "closest to its neighbours" (a cleaning judgement).
6. **An empty value is kept as a point with a quality and no value.**
   Details: "a row with no value" and "no row" are different defects (the missed-categories lesson,
   C-03). The real file has none. See the rollup gap below.
7. **A reading outside its experiment window is stored, counted and makes the run exit 1.**
   Details: start inclusive, end exclusive. Dropping it would be a cleaning call. The real file
   has none.
8. **Ingest is hard to misuse.** The CSV's SHA-256 is checked before any write; the run refuses
   (exit 2) on a wrong fingerprint, a missing database, a bad header, or an unreachable server.

## Findings that were not in the plan

1. **Partial accept works as documented on the v3 endpoint, and the client's default endpoint
   ignores it.**
   Details: probed on the 3.11.2 container with one batch of one good and one type-conflicting
   line. `accept_partial=True` on the v3 endpoint saved the good line and failed the other;
   `False` saved nothing. The v2 endpoint, which the Python client uses by default, saved nothing
   whatever the flag was. Ingest sets `use_v2_api=False, accept_partial=False` explicitly. This
   closes the open item from the plan.
2. **The first version of the private stack script threw away its own admin token on a second
   `up`.** Caught on the first manual run and fixed; logged in `docs/MISTAKES.md` as the token-loss mistake (E-08), with a test.
3. **The dev `.env` is protected.** `up` copies a dev `.env` to `.env.pre-verify` before writing
   the private one, and `down` puts it back (the dev token cannot be recovered if lost).

## Speed

Details: 520,005 rows in 72.1 s on native Windows with local Docker, about 7,200 rows per second,
52 batches of 10,000 lines. Phases: fingerprint 0.2 s, read, validate and sort 16.1 s, resolve and
write 53.7 s, count back 1.9 s. The earlier scratch run of the same file took 70.6 s, so expect a few seconds of spread. Not tuned. Batch size 10,000 is a starting value
and was not compared with others.

## Owed review: the schema doc and the rollup function

The review owed since the first milestone is done in a light form here. It found one stale number
and one real gap.

1. **Schema doc: the state-table size was off by one.** It said about 73 rows; the database holds
   74 (7 to 19 `process_state` and 3 to 5 `valve_state` per experiment, matching the doc's ranges).
   Fixed in `docs/schema.md`, which also gained the conflicts table. The 150-series claim, the
   quality counts and the two-table split all agree with the loaded data.
2. **Rollup function: it fails on a stored point with no value.** The aggregation takes `min()`
   and `sum()` over every value, and an empty-value point has none, so it raises `TypeError`.
   Details: confirmed with a two-sample call to `compute_rollup`. The real file has no such
   point, so nothing fails today, but M2 now stores them on purpose (decision 6). M3 must decide
   whether the rollup skips them or counts them as missing. Parked in the milestone record's next
   steps, not fixed here, since changing the M1 rollup is outside M2's scope. The other design
   choices in that file match ADR-0011 (population standard deviation, verdict-independent
   columns over all samples, predicate injected).
