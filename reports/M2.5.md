# M2.5 report: post-ingest profiling

Date: 2026-11-23   Branch: `m2.5-profiling` (cut from `m2-ingestion`, not committed yet)   Added scope, not in the brief

## In one paragraph

There is now a command that measures the data stored in InfluxDB and writes the numbers to a
file, without judging any reading. On the real data it covers 150 series, 6 experiments, 24
cross-checks between related signals and all 519,980 stored points. It takes about 16 seconds. I
checked every number by recomputing it separately in plain Python from simple pulls of the raw
points: 0 differences. Running it again gives the same file, and a brand-new database loaded from
the raw CSV gives the same file too.

Details: command `python -m scripts.post_ingest_profile`, run on the dev `dac_raw`. Committed
outputs: `reports/post_ingest_profile.json` (shape pinned by
`contracts/post_ingest_profile.schema.json`) and `reports/post_ingest_profile.md` (the same
numbers as tables). Decisions: [ADR-0014](../docs/decisions/ADR-0014-post-ingest-profiling.md).
Scenario list: `.workflow/dac.md` (S25.1 to S25.22).

## What I need from you

Nothing blocks. Three things are worth your eyes, in this order.

1. **I moved one group of measures out of SQL into Python.** The correlations and fitted lines
   (slope, intercept, R squared) are computed in Python on pulled pairs, not in the database.
   The plan said relationships run in SQL. Details: on the second run of the real data two of 24
   `regr_intercept` values differed in the 9th digit. An intercept here is about 0.001 computed
   from terms near 30,000, and the engine adds numbers in a different order from run to run. That
   would break "a re-run gives the same file". The plan already allowed a per-measure fallback to
   a Python pull (plan decision 4); this is that fallback, limited to the fits. Residuals,
   ratios and differences stay in SQL. Python sums are exactly rounded (`math.fsum`), so the same
   pairs always give the same bits. Overturn it if you want the relationships all in SQL; the
   cost is a re-run that can differ in the last digit.
2. **Three small definitions I chose.** All three are in ADR-0014 and any can be changed.
   Details: (a) `instants_unmatched` counts points of the first-named signal (power, outlet CO2,
   current, pressure drop) that found no partner at the exact same instant; the plan did not say
   which side. (b) "Relative residual" is the absolute residual divided by power, for power above
   zero. (c) Standard deviation is the sample one (n minus 1).
3. **The span probe answered, which is good news you should state carefully.** One query for
   all numeric points from 2026-03-02 to 2026-06-15 (105 days) was accepted and returned 519,906
   points, equal to the sum of the six per-experiment counts. Details: this says the roughly
   72-hour limit did not stop a 105-day query on this 520k-point data. It does not say why, and
   ADR-0004 ties the limit to a file count, so a larger data set may behave differently. I
   narrowed the open question (U-05) and left it open for Grafana's wide time picker (M6) and the
   overlay (M5).

Merging to `master` still waits for you. Nothing is committed or pushed yet.

## Four things this server got wrong

Each one was found because the SQL answer disagreed with the Python recomputation. All are
worked around, tested, and recorded in ADR-0014.

1. **A conditional count counted a missing value as a match.** `COUNT(*) FILTER (WHERE ...)`
   counted rows whose condition was empty. Gaps and below-range counts were one too high.
2. **Negative zero is not equal to zero.** One real current reading is `-0.00`; it was counted
   below the documented minimum of 0. Counting a sign, not a value.
3. **The percentile function is only accurate to about 7 digits.** 95 percent of `0.0, 0.39,
   0.41` came back as 0.40799998. Percentiles are now computed by rank in the query.
4. **The engine's sums are not reproducible in the last bits.** This broke the identical re-run
   for fitted intercepts, so the fits are done in Python (first item under "What I need from you").

Details: unit tests read the SQL text and fail if `FILTER (` or `PERCENTILE_CONT(` comes back or
if signed zero is not normalised. The fixture's end-to-end run exercises the rest.
