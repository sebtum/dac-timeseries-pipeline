## What changed, in plain words

- **A verdict for every reading.** Three new tables sit next to the raw ones in `dac_raw`. One holds a
  row per numeric reading with its raw value, the value we use, the acquisition flag, the verdict and
  the reason. One holds the two state signals as intervals (each state lasts until the next one). One
  holds gaps and stuck stretches.
- **Rules per signal.** Each signal has physical limits, a normal step size and the rules that apply to
  it. A setpoint and the state signals are exempt from the spike and stuck-sensor rules, for stated
  reasons.
- **Proof by counting.** The run reads back what it wrote and checks that every series has as many
  processed rows as raw readings, and that the raw tables did not change.
- **The rollup reads the verdict.** One-minute buckets are now computed over accepted readings only.

Details: tables `readings_processed`, `state_intervals`, `quality_intervals`
([schema](../docs/schema.md)). The rules read only `pipeline/cleaning_policy.py`; nothing is learned
from the data at run time. Exit codes: 0 written and balanced, 2 refused (nothing written, database
never created), 3 a query or write failed, 4 written but counts do not balance.

## Calls I made that you should review

Each one can be overturned. Each has the decision, why, and the option I rejected.

1. **EXP_004 air flow from 09:00 to 10:00 is a sensor fault.** We exclude those 3,600 readings. Why:
   the air-flow reading falls about 60 times and its noise collapses, while fan speed, pressure drop
   and outlet CO2 stay the same, so the air did not really change. Rejected: keep the readings and
   let the comparison milestone decide.

   Details: caught by the stuck-sensor rule, not by a special case: its steps are about 0.4 against
   a normal 7.55. All 3,600 carry `outside_typical_range` too (below 1,000 m3/h). Metrics over EXP_004
   will lose an hour of air flow. A cleaning call, not a finding (ASSUMPTIONS A-07). Overturn by
   changing the policy table and bumping the version, then re-running both commands.

2. **Physical limits are stand-ins.** We have no instrument spans, so each limit is a wide bound that
   contains the typical range. Rejected: limits learned from the data.

   Details: ASSUMPTIONS A-05. A pH is 0 to 14 by chemistry. Current allows down to -2 A because small
   negative readings (down to -0.69 A) are offset around zero. The four real hits are far outside.

3. **UNCERTAIN counts as excluded.** Why: the rollup decision already treated UNCERTAIN as BAD, so
   this stays consistent. Rejected: accept UNCERTAIN with a note.

   Details: 230 readings, all in EXP_004 pressure (200) and EXP_005 ambient pressure (30).

4. **Typical-range violations are a note, not an exclusion.** Why: EXP_002 was run up to 350.55 A
   against a typical 260 A, and that is the experiment's design. Rejected: exclude everything
   outside the data dictionary's range.

   Details: 10,242 readings carry the note and are accepted. The note makes them easy to filter.

5. **Solar uses an exact-repeat rule.** For solar power a stretch counts as stuck only if the value
   repeats exactly (and not at night). Why: at dawn solar power rises slowly and the shared rule called
   that ramp stuck. Rejected: exempt solar entirely (would miss a frozen sensor).

   Details: ADR-0015 decision 25. Limit: a solar sensor frozen with a little noise is not caught.

6. **A stuck stretch needs at least 5 small steps in a row.** Why: on smooth signals (pH, ambient
   pressure) small steps happen by chance, and the first run flagged 7 chance readings. Rejected:
   make "small" smaller (would weaken the noise-collapse detection that finds the air-flow fault).

   Details: ADR-0015 decision 24. The five real stuck features keep identical counts.

7. **Processed tables live in the raw database.** Why: they can only be rebuilt while raw exists, so
   they should expire with raw, and it keeps one of Core's five database slots free. Rejected: a
   fourth database for processed data. Wart: the name `dac_raw` now also holds derived tables.

8. **The rule set has a version tag, with a fingerprint test.** Every processed row carries
   `m3-v1`; a test fails if a number in the table changes without a new version. Why: a new rule set
   writes new rows beside the old ones instead of half overwriting them. Rejected: version as a field.

   Details: a later write of the same key without a field keeps the old value on this server
   (measured), so overwriting in place would leave stale fields.

9. **The rollup is an external job and reads the verdict (ADR-0011 addendum).** Why: the verdict is now
   in InfluxDB, and testing a plugin needs a plugin-enabled server. Rejected: a Processing Engine
   plugin.

   Details: adds `count_no_value`; closes the open question U-04. The addendum is not a reversal.

## Known limits

| Limit | Why it matters |
|---|---|
| A burst of more than 5 bad readings looks like a step to the spike rule | Limits or the stuck rule may still catch it. |
| A solar sensor frozen with a little noise is not caught | The solar rule only sees exact repeats. |
| The thresholds come from six 2-hour runs | A longer or noisier data set may need them re-set, which is a new policy version. |
| Rollup stale field | A later write without a field keeps the old value on this server. If rows of one policy version changed so a bucket's included count fell to 0, a re-run would keep its old mean. The design prevents it by construction (rule changes bump the version). Read mean, std and median only where `count_included > 0`. |
| Rollup is slow and quiet | About 12 minutes for 16,256 buckets, and it prints only when an experiment finishes. The streaming read is the likely cost; not profiled. |
| The end-to-end rollup test shares the cleaning's database | Core allows 5 databases and 4 already exist when it runs. |
| One series window at a time | Continuous data needs time-chunked processing; not built. |
